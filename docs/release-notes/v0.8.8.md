# DSH Desktop v0.8.8

**主题：修好「登录失败」，并把登录页开在应用内。**（跟随的官方 harness 仍是 `@deepseek-ai/dsh` 0.1.7-alpha.2）

## 根因：不是登录流程坏了，是 Host 的 HTTPS 被挡了

真机诊断链（2026-09-23，本机）：

```
[deepseek-account] request  { path: '/auth-api/v0/dsh/auth_init', method: 'POST' }
[deepseek-account] request failed { path: '/auth-api/v0/dsh/auth_init', errorCode: 'network' }
```

`auth_init` 连**请求都没发出去**：拿 TLS 链一看，`*.deepseek.com` 的证书链被
**卡巴斯基的「加密连接扫描」**重建（`Kaspersky Anti-Virus Personal Root Certificate`，自签）。
Windows/浏览器信任它，而 **Node 只认自己打包的 CA 列表** → Host 进程里所有 HTTPS 都
`SELF_SIGNED_CERT_IN_CHAIN`（登录的 `auth_init`、模型请求、余额查询一起挂）。

同一时刻的对照：应用内网页（Chromium 栈）与 electron-updater 都正常 —— 这正好是"网页能上、应用连不上"的典型症状。

## 三处改动

1. **Host 与 pnpm 改用操作系统证书库**（`--use-system-ca`，Node 24 的官方开关，也可放在 `NODE_OPTIONS` 里）。
   一处生效、全链受益：账号登录、模型请求、余额查询、插件安装（pnpm 从 registry 拉包同样要过这道 TLS）。
2. **壳自己的 API Key 自检改走 Chromium 网络栈**（`net.fetch`）——主进程的 Node fetch 有同样的 CA 问题。
3. **登录页默认开在应用内窗口**（你要的"内置网页打开"）：
   - 独立 session 分区（`persist:dsh-login`，保留平台登录态），`sandbox`、无 preload；
   - 导航白名单：只允许**平台授权域**与**本机回环回调**（Host 的 `/oauth/callback`），
     其它 http(s) 一律交给系统浏览器（页面里的帮助/条款等外链）；
   - **加载失败或建窗失败自动退回系统浏览器**（"跳转打开"也保留），
     想强制用浏览器：设 `DSH_DESKTOP_LOGIN_BROWSER=1`；
   - 授权成功自动关窗 + 通知一次；失败/超时/取消也会关窗并把主窗口唤回前台。

## 实测（同一台机器，临时 profile，A/B）

| | 不带 `--use-system-ca`（0.8.7 现状） | 带 `--use-system-ca`（0.8.8） |
|---|---|---|
| `account/startSignIn` 终态 | `failed` / `errorCode: network` | `waiting-browser` ✅ |
| 是否拿到授权链接 | ❌ | ✅ `https://platform.deepseek.com/dsh/authorize` |

## 如果你还在用 0.8.7（不想马上更新）

- 卡巴斯基 → 设置 → 安全威胁 → **加密连接扫描**：关掉，或把 `platform.deepseek.com` / `api.deepseek.com` 加进排除项；
- 或者直接装本版：安装后点左下角「登录」，授权页会**在应用内窗口**打开，完成即自动关窗。

> 顺带提醒：这类"安全软件扫描 HTTPS"也会影响插件安装（pnpm 拉包）与模型请求 —— 本版的 `--use-system-ca`
> 把它们一起修好了；将来如果再把扫描打开，也不需要改配置。
