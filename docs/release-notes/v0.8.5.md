# DSH Desktop v0.8.5

跟随官方最新 harness 同步：`@deepseek-ai/dsh` 0.1.7-alpha.1 → 0.1.7-alpha.2。

- 随包运行时（dsh + Node + pnpm）按绑定版本重建，`verify:runtime` 逐文件 sha256 校验通过
- typecheck + 单元测试 + e2e（真实 dsh + 官方认证 Web Host + bridge 契约）全绿
- 壳版本 patch+1（v0.8.5）：应用内「检查更新」即可自动下载安装，无需手动重装

本次除了跟随官方版本，还修掉两个本壳自己的偏差（详见正文）：

## 1. 左下角账号登录能用了（官方桌面身份的适配）

官方桌面端交给启动器的 profile **身份名**是 `desktop`，而本壳此前把「目录名」和「身份名」一起改成了自有的
`dsh-workbench`——目录名这个改动是必须的（官方 CLI 硬拒绝 `--profile desktop`），但身份名跟着改，就让官方组合树
里两处 desktop-only 的行没挂上：账号插件因此**不带** `x-client-platform: desktop-win` 请求头，平台在
`auth_exchange` 阶段拒绝授权（插件把"被拒"与"断网"归成同一类，日志里看起来只是 `errorCode: 'network'`，
所以很难查）。现在**目录名保留自有，身份名照官方报 `desktop`**。

顺带把官方桌面端围绕登录做的原生动作补齐（`apps/desktop/src/main.ts` 的等价物）：

- 尝试进入「等待浏览器」时**自动用系统浏览器打开授权页**，链接附 `theme=dark|light` 跟随应用配色；同一次尝试只开一次；
- 授权**超时/失败**时把主窗口唤回前台，并按原因给出中文提示（网络 / 凭据存储 / 超时 / 平台拒绝）；
- 应用文档根补上 `data-platform`（桌面专属样式的开关，官方 `preload-platform.ts` 的等价物）。

状态由桥接插件在宿主进程内订阅账号服务后推给壳（`account.changed`）——**凭据、token、用户资料一律不过桥**。
用量/充值按钮当前仍在系统浏览器打开（官方那种应用内平台视图尚未做）。

## 2. 插件残留与「cannot resolve profile bundle」的根因修掉了

两个根因都是官方事务语义与本壳换 pnpm 主版本的叠加，不是官方行为变化：

1. 官方插件管理器的安装/升级失败**只回滚 `package.json` + `pnpm-lock.yaml`，`node_modules` 不回滚**；
2. 跨壳版本换 pnpm 主版本后 store 布局换代（`ERR_PNPM_UNEXPECTED_STORE`），每次包操作都会失败。

于是 profile 里会同时出现「清单声明了、盘上没有」（真机：`dsh-better-sidebar`，harness 报
`cannot resolve profile bundle …`，0.1.7 之前直接让 Host 起不来 → 连续三次把应用推进安全模式）与
「盘上有、清单里没有」（真机：`dsh-commandcode-goat`、手链接进 `E:\Dsh\Plugins` 的 `dsh-opencode-go`，
也就是用户看到的"插件残留"）。

现在启动期做两件收敛（都不做插件管理，插件管理仍在官方「插件」页）：

- **bundle 对账加解析检查**：解析不出来（profile `node_modules` 与随包 dsh 树都没有）的 bundle 条目移出启用列表；
  依赖与已装包一律不动，插件在插件页里仍可见、可重装；
- **profile 依赖体检 + 修复**：缺包/锁文件脱节 → 随包 pnpm 跑一次 `pnpm install`；清单未声明、pnpm 也不认的
  插件目录 → 清除（链接只删链接本身）。判定为干净时什么都不做；离线失败不阻塞启动，6 小时内不重复同一状态的重试，
  日志与通知说清是哪一档。

## 3. 其它

- 对齐审查文档新增第六轮（`docs/OFFICIAL-ALIGNMENT-REVIEW.md` §10），逐条给出真机证据（日志、文件状态、官方源码位置）。
