# DSH Desktop v0.8.11

跟随官方 harness：`@deepseek-ai/dsh` 0.1.7-rc.2（与 v0.8.10 相同）。

**这一版的主题：把"会被杀软按文件判定"的那个散件从启动链路里拿掉——不再要求用户加白名单或重装。**

## 1. 真机复现的第三段证据（2026-09-25）

症状：应用一直弹「桌面运行时缺少随包文件（安装不完整，或被杀毒软件/安全软件的启发式规则隔离）：
· Host 入口 …\resources\dsh\node_modules\dsh-desktop-host\lib\index.js」。

按 `resources/dsh/desktop-runtime.json` 的 **10883** 条 sha256 清单逐文件对账，结论很干净：

- **只缺 `dsh-desktop-host/lib/index.js` 这一个文件**（7711 B，sha256 `8ece84a6…`），其余大小/哈希全对
  → 不是安装不完整，也不是文件被改写；
- 仓库 `resources/dsh/…` 与 `release/win-unpacked/…` 里那份与清单哈希完全一致 → 安装包里本来是完好的；
- 删除发生在应用**没有运行**的时间段（09-23 05:51 最后一次 `host ready` → 09-25 13:29 起连续失败）
  → 更像"后台扫描/信誉判定针对这个文件"，而不是运行期行为拦截。

那份文件是壳自己的代码（`packages/host/src/index.ts`，MIT 移植）的构建产物，内容没有混淆、没有载荷；
但它**摆放的形状**正好是启发式最敏感的：安装目录深层里一个未签名的脚本、会拉起子进程，
而且还是启动硬前提——所以被删掉之后，壳只能弹"加白名单后重装"。

## 2. 修法：Host 入口随壳打进 `app.asar`，运行时树那份降级为兜底

- `scripts/build.mjs` 把**同一份源码**产出 `dist/main/host-entry.cjs`（随 `files: dist/**` 进 **app.asar**）。
  Electron 的 asar 是单个归档，杀软无法像删散件那样只摘走里面一个文件；
- 入口 banner 把 `<runtimeDir>/node_modules` 加进自身模块搜索路径，`@deepseek-ai/*` 仍由随包运行时树提供
  ——"壳 + dsh + Node + pnpm 是一个签名更新单元"（D29）没有被拆开；`define: import.meta.main`
  让 CJS 形态下照旧直接执行；
- 新增 `src/main/hostEntry.ts` 决定用哪份入口：**壳自带副本优先 → 运行时树副本兜底 → 两处都没有才算损坏**；
  `resolveRuntime()`、`HostManager.spawn()`、`DesktopHostProcess` 全部走这个决策。
  于是**树里那份被杀软清掉时应用照常启动**，不再把用户卡在启动失败页上。

顺带的可见变化：`resolveRuntime()` 的关键文件清单不再把"运行时树里的 Host 入口"当硬前提；
`scripts/e2e-bridge.mjs` 改为优先用壳自带入口，让这条生产路径进 CI。

## 3. 验证（都在本机跑过）

- 契约测试：`test/host-entry.test.mjs`（决策顺序）+ `test/host-runtime-damaged.test.mjs`
  （树入口缺失、壳自带副本在场 → 照常 spawn，不报运行时损坏）；`npm run check` 共 **156** 项全绿；
- 打包形态实测：把 `dist/main/host-entry.cjs` 打进真 asar，用 Electron 44 以
  `ELECTRON_RUN_AS_NODE=1` 加载 → 完整引导真实 harness 并 `ready`（`dsh 0.1.7-alpha.2`，隔离 `DSH_HOME`）；
- 壳级实测：用仓库源码跑壳（独立 userData），进程命令行确认 spawn 的是 `dist/main/host-entry.cjs`，
  日志出现 `host ready: dsh … injections=11`；
- 随包运行时（dsh 0.1.7-rc.2 + Node + pnpm）按绑定版本重建，`verify:runtime` 逐文件 sha256 通过；
- typecheck + 单元测试 + e2e（真实 dsh + 官方认证 Web Host + bridge 契约）全绿。

## 4. 仍然要说清楚的边界

- 随包运行时是完整闭包，树里那份散件仍在安装目录里；杀软仍可能隔离它（并弹一条提示），
  但**应用不再受影响**——这正是本版要保证的；
- 要让启发式"停止怀疑"，唯一根治手段仍是**签名发布**（Azure Trusted Signing / SignPath Foundation /
  EV 证书）。本版继续做的是把"能被怀疑、且会致命"的形状拿掉；
- 彻底不弹那个提示，可以在此后的某次出包里用 `scripts/runtime-file-policy.mjs` 把树里那份散件一并剔除
  （会改变 `desktop-runtime.json` 清单，属于一次正常出包）。
