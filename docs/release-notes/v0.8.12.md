# DSH Desktop v0.8.12

**主题：先回到"能打开"，把自动跟随官方更新暂停，等上游稳定 + 补上桌面原生桥再接。**

## 1. 出了什么事（v0.8.11 装完打不开）

v0.8.11 跟随了官方 `@deepseek-ai/dsh` **0.1.7-rc.2**。安装后应用本身能启动、Host 也会 `host ready`，
但**工作台（Web UI）打不开**，日志里是：

```
workspace boot failed: web boot: 24 entries did not activate
@deepseek-ai/dsh-client-shortcuts: failed
@deepseek-ai/dsh-client-ui-shortcuts: pending (waiting for service: shortcuts)
…（其余 22 项同类 pending）
```

根因（逐行读 rc.2 客户端 bundle + 浏览器对照实验得出）：

- rc.2 的客户端模块系统改为"boot manifest + 批量加载"，其中 `@deepseek-ai/dsh-client-shortcuts`
  在 `detectEnvironment()` 判定为**桌面运行时**（`document.documentElement.dataset.platform` 存在）后，
  **强制要求** preload 提供 `window.dshDesktop.keyboard`，缺失就
  `throw new Error("Desktop keyboard bridge unavailable")` → 该模块 failed → 依赖它的 24 个 UI 模块全部 pending；
- 对照组：**同一个 host、同一份 manifest（65 条 entry、同一 rev）**，走官方 web 路径（浏览器直连）**完全正常**
  —— 所以不是 harness 有 bug，而是桌面壳必须提供的能力面变了；
- 而 `window.dshDesktop`（native keyboard / shortcuts 桥）是官方**未发布**的私有桌面壳才有的东西，
  我们这边没有，也就没法"改几行跟上"。

## 2. 这一版做了什么

1. **随包 harness 回到最后一个验证可用的 `0.1.7-alpha.2`**（`package.json.dshRuntime.dsh` 与
   `packages/host` 里跟随 dsh 的依赖一起回退），壳版本升到 v0.8.12 —— 装完能正常打开工作台；
2. **暂停自动跟随**：`.github/workflows/upstream-dsh.yml` 停用每日定时（`schedule` 注释掉），
   并新增"暂停守卫"步骤：即使手动触发也会拒绝升级随包 harness、写明原因并让这次运行失败，
   避免无人值守又自动发一版打不开的包；
3. **保留 v0.8.11 的杀软误报结构性修复**（Host 入口随壳打进 `app.asar`，运行时树里那份只作兜底，见 D50）；
4. 把"恢复自动巡检前必须补齐的桥接面"写进 `docs/DESIGN.md` D51（`window.dshDesktop.keyboard`
   = `subscribe/closeWindow`、`window.dshDesktop.shortcuts` = `get/edit/subscribe/recording/dispose`、
   以及 `document.documentElement.dataset.platform`）。

## 3. 验证

- 随包运行时按 `0.1.7-alpha.2` 重建，`verify:runtime` 逐文件 sha256 通过；
- `npm run check`（typecheck + 单元测试）与 `npm run e2e:bridge`（真实 dsh + 官方认证 Web Host + bridge 契约）全绿；
- 本地打包 `DSH.Desktop-0.8.12-setup.exe` 并实跑：Host `ready`、工作台正常加载，无 `entries did not activate`。

## 4. 什么时候恢复自动跟随

等上游稳定（rc 线不再变，或 stable 版把这套桌面桥的契约公开）后：
实现 D51 里列的 preload 桥 → 放开 workflow 的 `schedule` → 删掉"暂停守卫"步骤 → 正常巡检发版。
